# サーバー（Go）

センサーデバイスと BLE で、カメラ（Python）と画面（Unity）と WebSocket でつながり、届いたイベントで鍋の状態を変えて、画面にイベントを送るサーバー。要件定義書の 3 章・5.9・6.3〜6.6 に対応する。
今あるのは調味料（振り → グラム）、火の強さ（つまみ → 段階）、カメラの位置・切った・入れた・振り下ろしを画面に流すこと、リセット。焼き加減・工程・採点・提供は次の段階で足す（`docs/進め方_BLEとサーバー.md`）。

## 動かす

Go（1.25 以上）が入っていなければ、先に入れる（https://go.dev/dl/ 。Mac は `brew install go` でもよい）。

```sh
cd server
go run .                            # config.toml を読み、近くの omamagoto- のデバイスを全部探してつなぐ。止めるのは Ctrl+C
go run . 別の設定.toml              # 設定ファイルを変える
go run . --no-ble                   # BLE を使わない（デバイスの無い PC で、カメラと画面だけ試す）
go test .                           # テスト（実機は要らない）
go build .                          # 実行ファイル omamagoto-server（Windows は omamagoto-server.exe）を作る
```

- 1 つの実行ファイルで動く。展示用 PC には、作った実行ファイルと `config.toml` を置けば Go を入れなくてよい
  - Windows 用は、Mac でも `GOOS=windows GOARCH=amd64 go build .` で作れる
- Bluetooth が使えないときは「BLE が止まった。デバイスなしで続ける」と出て、カメラと画面だけで動き続ける

- macOS では、初回にターミナルへの Bluetooth の使用許可を求められる
- Ctrl+C で止めると、つないでいるデバイスを切ってから終わる。強制終了してもデバイスの再起動は要らない

表示の例（出したイベントだけを表示する）：

## 画面とカメラとのつなぎ方（WebSocket）

`config.toml` の `[ws]` の `listen` で待つ（今は `0.0.0.0:9000`。別の PC からもつなげる）。

| つなぐ所 | 相手 | やり取り |
| --- | --- | --- |
| `ws://<PC>:9000/screen` | 画面（Unity・`screen/index.html`） | サーバーが出したイベント（要件定義書 6.4）を、つながっている全部の画面に送る |
| `ws://<PC>:9000/camera` | カメラ（`camera/main.py`） | 6.3 の JSON を受け取る。パスを付けずに `ws://<PC>:9000` でつないでもカメラとして扱う |

画面に送るもの（共通ヘッダ `device`・`ts`・`seq` が付く。`seq` はサーバーを起動するたびに 1 から）

| event | いつ |
| --- | --- |
| `position` | カメラから位置が届いたとき（そのまま流す。`cam` は外す） |
| `swing` | カメラが振り下ろしを見たとき |
| `cut` | カメラが「切った」を確定したとき（`count` は今のピース数） |
| `add` | カメラが「フライパン・皿に入った」を確定したとき（`count` は増えた数） |
| `season` | 塩・こしょうを振ったとき |
| `fire` | つまみの段階が変わったとき。画面がつながったとき（`hello`）とリセットのあとにも、火がついていれば今の段階を送る |
| `reset` | リセットしたとき |

画面から受け取るもの

| event | サーバーがすること |
| --- | --- |
| `hello` | 画面がつながった。今の状態（火）を送る |
| `reset` | 鍋の状態（調味料・ピース数・フライパンの中身）を空にして、全部の画面に `reset` を送る。火はつまみの実際の位置なので戻さない |

まだ無いもの：`serve`（提供と採点）、`status`（デバイスの接続とバッテリー）、焼き加減、無操作の自動リセット

## 設定（`config.toml`、要件定義書 6.5）

- `[roles]`：デバイスの MAC アドレス → 役割（`salt`・`pepper`・`pan`・`knob`・`range`）。MAC アドレスはデバイスの画面の 1 行目に出ている。設定に無いデバイスがつながると、サーバーが MAC アドレスを表示する
- `[season]`：`grams_per_shake` は強さ 1 で 1 回振ったときのグラム数。強さが小さければその分少なくなる
- 書き換えたらサーバーを再起動する

## ログ（`logs/`、git には入れない）

起動ごとに `日時.jsonl` を作り、受け取ったもの（`in`）・出したもの（`out`）・接続と切断（`note`）を 1 行 1 JSON で書く。
役割に合わないイベント（塩のデバイスの `knob` など）は表示しないが、ログには残る。

## 作り

入り口（BLE・WebSocket）と本体を分け、入り口から本体へはチャンネルで 1 件ずつ渡す。goroutine を使うのは入り口と `main.go` だけにして、本体（`kitchen.go`）は普通のコードで書き、`go test` で確かめる。
全部 1 つのパッケージ（`package main`）。ファイルごとに `_test.go` のテストがある。

重複の判定：同じデバイスから、同じ起動のうちに受け付けた連番以下が来たら捨てる。デバイスが再起動すると `seq` は 1 から、`ts` は 0 から数え直すので、`ts` が戻っていたら再起動とみなして受け付ける。

| ファイル | 役割 |
| --- | --- |
| `main.go` | 入り口（BLE・WebSocket）からのメッセージを 1 件ずつ本体に渡し、出たイベントを表示してログに残し、画面に送る。Ctrl+C で入り口に止めるよう伝える |
| `kitchen.go` | 本体（鍋の状態）。重複を捨てる、役割に合わないイベントを無視する、振り → グラム、つまみ → 火の強さ、カメラのイベント → 画面へ、リセット |
| `ws.go` | WebSocket の入り口（`coder/websocket`）。`/screen` の画面に全部のイベントを配り、`/camera` のカメラから受け取る |
| `event.go` | イベントの型（要件定義書 6.2 のデバイスから、6.3 のカメラから、6.4 のサーバーから）。JSON の読み書き |
| `config.go` | 設定ファイルを読む（`BurntSushi/toml`） |
| `eventlog.go` | ログファイルに書く |
| `ble.go` | BLE の入り口（`tinygo.org/x/bluetooth`。Windows・macOS・Linux）。デバイスを探し、1 台ずつ専用の goroutine でつないで通知を受ける。切れたら goroutine が終わり、探し直して、次に見つけたときにつなぎ直す |
| `linebuffer.go` | 分けて届いた通知を改行までつなげて 1 行にする |

決めている値（`ble.go`）：

| 値 | 理由 |
| --- | --- |
| 接続のタイムアウト 3 秒 | 10 秒だと、サーバーを再起動したあとの再接続に 11〜12 秒かかった（2026-10-13 の実測） |
| つながっているかの確認 1 秒ごと | 切断の通知が来ない OS があるため |
| 名前を待つのは最大 1 秒 | 名前（`omamagoto-5C3C`）はスキャン応答に入っていて、最初の広告より少し遅れて届く。待たないと名前の代わりに ID が出る |
| デバイスが切れたら探し直す（念のため 10 秒ごとにも） | macOS は 1 回の探す（スキャン）のうちに同じデバイスを 1 回しか知らせないため |
| 止めるときは切断が終わるまで最大 2 秒待つ | 切らずに終わると、デバイスが広告を止めたままになり、次の起動でつながるまで 10 秒以上かかる |

OS ごとに気をつけていること：

- macOS：Bluetooth の切断は待たずに戻るので、切れるまで待ってから終わる。デバイスのアドレスは MAC ではなく、Mac が付けた ID（UUID）になる（役割は JSON の `device` の MAC で決めるので困らない）
- Windows：`Disconnect` の中で後始末をするので、1 台につき 1 回だけ呼ぶ。**Windows の実機ではまだ試していない**

## Rust 版から Go 版にしたとき（2026-11-26）

外から見た動き（画面に送る JSON、表示、ログの形、設定ファイル）は Rust 版と同じにした。同じ入力を両方に送って、画面に届く JSON 11 件とログ 32 行が同じになることを確かめた（`docs/テスト記録.md`）。
違うのは次だけ：

- 読めない行の表示のエラー文が日本語になった（例：「JSON として読めない（1 バイト目）」）
- `0.0.0.0:9000` で待つとき、IPv4 だけでなく IPv6 でもつなげる
- Ctrl+C だけでなく、`kill`（SIGTERM）で止めたときもデバイスを切ってから終わる
- 画面の受け取りが遅れたときは、画面ごとに 1024 件まで待ち、あふれた分を捨てて表示する（Rust 版は全部の画面で 1024 件）
