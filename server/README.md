# サーバー（Rust）

センサーデバイスと BLE でつながり、届いたイベントで鍋の状態を変えて、Unity に出すイベントを作るサーバー。要件定義書の 3 章・5.9・6.4〜6.6 に対応する。
今あるのは調味料（振り → グラム）と火の強さ（つまみ → 段階）。Unity・カメラとの WebSocket、工程・採点・リセットは次の段階で足す（`docs/進め方_BLEとサーバー.md`）。

## 動かす

```sh
cd server
cargo run                           # config.toml を読み、近くの omamagoto- のデバイスを全部探してつなぐ。止めるのは Ctrl+C
cargo run -- 別の設定.toml          # 設定ファイルを変える
cargo test                          # Mac 上のテスト（実機は要らない）
```

- macOS では、初回にターミナルへの Bluetooth の使用許可を求められる
- Ctrl+C で止めると、つないでいるデバイスを切ってから終わる。強制終了してもデバイスの再起動は要らない

表示の例（出したイベントだけを表示する）：

```
設定 config.toml：デバイス 1 台
ログ logs/20261013-132401.jsonl
13:24:03.857 omamagoto-5C3C 接続
13:26:10.159 → salt +0.39g（合計 0.45g）
13:27:01.429 → 火 強
```

## 設定（`config.toml`、要件定義書 6.5）

- `[roles]`：デバイスの MAC アドレス → 役割（`salt`・`pepper`・`pan`・`knob`・`range`）。MAC アドレスはデバイスの画面の 1 行目に出ている。設定に無いデバイスがつながると、サーバーが MAC アドレスを表示する
- `[season]`：`grams_per_shake` は強さ 1 で 1 回振ったときのグラム数。強さが小さければその分少なくなる
- 書き換えたらサーバーを再起動する

## ログ（`logs/`、git には入れない）

起動ごとに `日時.jsonl` を作り、受け取ったもの（`in`）・出したもの（`out`）・接続と切断（`note`）を 1 行 1 JSON で書く。
役割に合わないイベント（塩のデバイスの `knob` など）は表示しないが、ログには残る。

## 作り

入り口（BLE）と本体を分け、入り口から本体へはチャンネルで 1 件ずつ渡す。非同期（tokio）を使うのは入り口と `main.rs` だけにして、本体（`kitchen.rs`）は普通のコードで書き、`cargo test` で確かめる。

重複の判定：同じデバイスから、同じ起動のうちに受け付けた連番以下が来たら捨てる。デバイスが再起動すると `seq` は 1 から、`ts` は 0 から数え直すので、`ts` が戻っていたら再起動とみなして受け付ける。

| ファイル | 役割 |
| --- | --- |
| `src/main.rs` | 入り口からのメッセージを 1 件ずつ本体に渡し、出たイベントを表示してログに残す。Ctrl+C で入り口に止めるよう伝える |
| `src/kitchen.rs` | 本体（鍋の状態）。重複を捨てる、役割に合わないイベントを無視する、振り → グラム、つまみ → 火の強さ |
| `src/event.rs` | イベントの型（要件定義書 6.2 のデバイスから、6.4 のサーバーから） |
| `src/config.rs` | 設定ファイルを読む |
| `src/event_log.rs` | ログファイルに書く |
| `src/ble.rs` | BLE の入り口。1 秒ごとにデバイスを探し、1 台ずつ専用のタスクでつないで通知を受ける。切れたらタスクが終わり、次に見つけたときにつなぎ直す |
| `src/line_buffer.rs` | 分けて届いた通知を改行までつなげて 1 行にする |

決めている値（`src/ble.rs`）：

| 値 | 理由 |
| --- | --- |
| デバイスを探す間隔 1 秒 | 見つけてからつなぐまでの遅れを小さくする |
| 接続のタイムアウト 3 秒 | 10 秒だと、サーバーを再起動したあとの再接続に 11〜12 秒かかった（2026-10-13 の実測） |
| つながっているかの確認 1 秒ごと | 切断の通知が来ない OS があるため |
