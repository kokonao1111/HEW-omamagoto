### 0.6 続きを作る AI へ（つまずいた所）

- 形はすべてコード（`Assets/Scripts/Editor/Kitchen*Builder.cs`）。シーンを手で直さず、コードを直して「キッチンを作り直す」→ シーンを保存。寸法は現実の mm（x 右・y 奥・z 上）で書き、`KitchenLayout.ToWorld` で Unity の m に直す
- 作り直した直後に、再生していないシーンの画面が白っぽくかすむことがある → シーンを開き直すと直る。映り込み（`KitchenReflectionProbe`）は `Kitchen` の外に置いて使い回す（消して作ると画面が真っ白になる）
- 光る物は URP の **Unlit** で作る（Lit の Emission は、読み込み直すと消える）
- 穴の細かい模様を切り抜き（Cutout）で作ると、しま模様（モアレ）が出る → 半透明＋ミップマップ（電子レンジの網）
- Test Runner で PlayMode のテストを流すと、Project Settings の Enter Play Mode Options が変わることがある。流したあとに戻す（オフ）。`Run In Background` はオンのまま
- 写真の素材のざらつきの画像は、`unity/tools/rough_to_mask.py` で Unity の mask にする。炎・湯気・網目などの自作の画像は `unity/tools/make_textures.py`
- 素材を足したら、`unity/Assets/CREDITS.md` に出どころを書く（CC0 か自作だけ）

## 1. 作業のルール（必ず守る）

- **git のコミット・プッシュはしない**。ユーザーが自分でする。「git に入れて」と言われたら、ファイルをリポジトリのフォルダーに置くこと。区切りがよいときは、コミットメッセージの案だけ出す
- **大きく変わる変更は、する前にユーザーに伝える**（フォルダーの構成、要件定義書の中身、ほかの人の担当のフォルダーなど）
- ほかの担当のフォルダー（`server/`・`device/`・`camera/`・`train/`・`screen/`）は、頼まれない限り変えない。読むのはよい
- 要件定義書・設計書などの文書は、`docs/` に Markdown で書く（claude.ai のドキュメント機能は使わない）
- 返事は、短く、やさしい日本語で
- **コードは、人間がパッと見て読みやすく書く**。名前でわかるようにし、関数・クラスは短く役目を 1 つに、凝った書き方より素直な書き方。何のためのコードかを短い日本語のコメントで書く（2026-11-09 ユーザーの希望）
- **OpenAI の API キーは、ファイルに書かない・チャットに貼ってもらわない**。ユーザーが自分のターミナルで環境変数に入れる（下の 6 章）
- 素材（3D モデル・テクスチャ・音）は、使ってよいライセンス（CC0 など）のものだけ。出どころを `unity/Assets/CREDITS.md` に書く
- キャラクターはオリジナル（既存のキャラクターに似せない）
- **やったことを `docs/作業記録_Unity.md` に書く**。作業の区切りごと（ユーザーにコミットを勧める前）に、いちばん上に足す。書き方はそのファイルの先頭のとおり。ほかの PC の Claude やチームは、会話の履歴を見られないので、このファイルだけで今の状態がわかるように書く
- 会話を始めたら、まず `git pull` してあるか確かめ、このファイルと作業記録を読んでから作業する

このルールは、この PC の Claude のメモリにも保存しておく（次の会話でも守れるように）。

## 2. 作品のこと（短く）

HAL の HEW（2027 年 3 月）に出すチーム制作「リアルおままごと調理システム」。机の上のおもちゃのキッチンで料理のまねをすると、カメラとセンサーが動きを読み、画面の中では本物の料理をしているように見える。

```
おもちゃ（包丁・野菜・まな板）── カメラ 3 台 ── Python（camera/）──┐
塩・こしょう・コンロつまみ（M5StickS3）── BLE ──────────────────┤
```

- 詳しくは `docs/要件定義書_v1.md`（特に 5.10 画面、6.4 サーバー → Unity のイベント）

## 5. これからやること（この順で）

最初に立てた計画。**どこまで済んだかは 0.2**。

### 5.0 最初にユーザーと決めること

1. **Unity のバージョン**：要件定義書は「Unity 2022 LTS」。今から始めるなら、Unity Hub でいちばん新しい LTS（Unity 6 の LTS）を勧める（2022 LTS は古く、サポートも終わっているはず。Hub で確かめる）。変えるなら要件定義書の 10 章を直す案をユーザーに出す。チーム全員で同じバージョンにする
2. **描画の方式**：HDRP（リアルさ重視。展示用 PC は NVIDIA の GPU なので候補）か URP（軽い）か。3DGS の背景（UnityGaussianSplatting）が、選んだ方式で動くかも確かめる

### 5.1 準備

1. この PC に Git、Git LFS、Unity Hub、決めたバージョンの Unity を入れる
2. `git lfs install`（この PC で 1 回だけ）
3. `main` を最新にして、新しいブランチ（例：`feature/unity-screen`）を作る
4. リポジトリの直下に `unity/` を作り、そこを Unity のプロジェクトにする（`unity/Assets`・`unity/Packages`・`unity/ProjectSettings` になるように）
5. `unity/.gitignore`：`Library/` `Temp/` `Obj/` `Build/` `Builds/` `Logs/` `UserSettings/` `MemoryCaptures/` `.vs/` `.idea/` `*.csproj` `*.sln` など（Unity の標準のもの）
6. `unity/.gitattributes`：大きいファイル（`*.fbx` `*.obj` `*.glb` `*.png` `*.jpg` `*.psd` `*.tga` `*.exr` `*.hdr` `*.wav` `*.mp3` `*.ogg` `*.mp4` `*.ply` など）を LFS に回す。**`unity/` の中だけ**にかける（リポジトリの直下にかけると、今ある `screen/assets` の画像まで巻き込む）
7. Unity の設定：Asset Serialization を Force Text、メタファイルを表示（どちらも今の Unity は最初からそう）。`.meta` ファイルは必ず git に入れる
8. `unity/README.md` に、開き方・動かし方を書いていく

ここまでできたら、ユーザーにコミット・プッシュしてもらう（コミットメッセージの案を出す）。

### 5.2 イベントを受け取る（WebSocket）

- 受け取るイベントは要件定義書 6.4：`position` `swing` `cut` `add` `season` `fire` `serve` `reset` `status`
- 接続先は `ws://localhost:9000/screen`（three.js 版と同じ）。変えられるようにしておく。サーバーが送るもの・受け取るものは `server/README.md` の「画面とカメラとのつなぎ方」
- つながったら `{"device":"screen","event":"hello"}` を 1 回送る（サーバーが今の火の段階を送り返す）
- 画面でリセットするときは `{"event":"reset"}` をサーバーに送る（サーバーの調味料なども 0 に戻り、全部の画面に `reset` が来る）
- `seq` はサーバーを起動するたびに 1 から。つなぎ直したら、前の `seq` は忘れる
- 切れたら自動でつなぎ直す。つなぎ直している間は、画面の隅に小さく出す
- ライブラリは要件定義書では NativeWebSocket。`System.Net.WebSockets.ClientWebSocket` でもよい
- 位置は Lerp でなめらかにする

### 5.3 サーバーなしで試せるようにする（この PC にはセンサーもカメラもない）

- Unity の中に、キーでイベントを出す仕組みを作る（three.js 版と同じキー：K 振り下ろす、C 切る、A 入れる、S/P 塩・こしょう、0〜3 火、Enter 提供、R リセット、D デモ）
- サーバーなしのときに流すデモ（three.js 版の台本と同じ流れ）
- 本物のサーバーは、この PC でもデバイスなしで動く：`cd server` → `cargo run -- --no-ble`（Rust を入れる）。カメラのふりをして `ws://localhost:9000/camera` に 6.3 の JSON を送れば、サーバーを通って画面に届く
- あると便利：カメラのふりをして、台本どおりに 6.3 のイベントを送る小さなプログラム（Python の `websockets`）。置き場所は `unity/tools/`

### 5.4 キッチンの画面（横のモニター）

- まな板・コンロ・皿・電子レンジを、現実のキッチンと同じ配置で置く（4 章）
- 包丁・にんじん・フライパン・塩とこしょうの容器を 3D で置き、イベントで動かす
- 切る演出（1 回切ったら細かく切れる。見せ方はユーザーと決める）、フライパンに飛ぶ、塩・こしょうが降る、火がつく、焼けて色が変わる、湯気
- にんじん以外の野菜・レシピは未定。まずはにんじん 1 本で作る

### 5.5 お客さんの画面（縦のモニター）

- 仮想のお店。オリジナルのクマのお客さん
- 料理が届く → 食べる → 点数とコメント → リアクション（喜ぶ・普通・顔をしかめる の 3 種類以上）
- 2 台のモニターは、Unity のマルチディスプレイで出す（`Display.displays[1].Activate()`。エディターでは Game ビューの Display 2 で確かめる）。縦のモニターは Windows 側で縦向きにする

### 5.6 料理の写真

- `screen/dish_server.py` をそのまま使う。Python の標準ライブラリだけで動くので、この PC でも動く
- 送り方：`POST http://localhost:9001/dish`、本文は JSON `{"prompt": "指示の文", "image": "data:image/jpeg;base64,..."}`。返事は `{"image": "data:image/jpeg;base64,..."}`
- 返ってこない（45 秒）・失敗したときは、用意した写真（`screen/dishes/` の `good` `burnt` `undercooked` `salty`）から選んで出す
- 指示の文は `dishPrompt()`（`screen/index.html`）を C# に写す
- **本番の写真の元は、カメラが撮ったおもちゃの皿の写真**（3 章）。誰が `dish_server.py` に頼むか、できた写真をどう Unity に渡すか（`serve` に写真を付けるなど）はまだ決まっていない。なので、写真を頼む所は 1 つのクラスにまとめて、あとで差し替えられるようにする。今のテストでは、Unity の中の皿をカメラで撮って送ってよい
- 6.4 のイベントに項目を足す必要が出たら、要件定義書の変更案としてユーザーに出す

## 7. ほかの PC とつなぐとき

- 開発中は、Rust のサーバーやカメラは別の PC（Mac）で動くことがある。そのときは `localhost` の代わりに、その PC の IP アドレスにする（例：`ws://192.168.x.x:9000/screen`）。サーバーを起動すると「別の PC からは ws://…」とアドレスが出る。ファイアウォールで許可が要ることがある
- 展示用 PC では、サーバー・カメラ・`dish_server.py`・Unity を全部 1 台で動かすので、`localhost` のままでよい
- three.js 版の画面どうしのやり取り（BroadcastChannel）は、Unity では使わない（Unity は 1 つのアプリで 2 画面を出す）
