# 進め方：BLE 通信とサーバー

センサーデバイス（M5StickS3）から展示用 PC のサーバー（Go。2026-11-26 までは Rust）までを BLE でつなぎ、
「振る・回す → サーバーで鍋の状態が変わる」までを動かすための作業計画。
進んだら「状態」と「やったこと」を書き換える。テストの結果は `docs/テスト記録.md` に書く。

## 決めたこと（2026-10-13）

| 項目 | 決定 | 理由 |
| --- | --- | --- |
| 通信 | BLE。デバイスが周辺機器、展示用 PC が親 | 電池の持ち。会場の Wi-Fi・テザリングに依存しない |
| 受け側 | 展示用 PC の Bluetooth で直接受ける | 展示用 PC は 30 万円程度の高性能機（Bluetooth 5）。ESP32 を USB 受信機にする案は、PC で安定しなかったときの予備 |
| サーバー | Rust のまま → **2026-11-26 に Go へ移した**（⑤） | 理由はまだ書いていない（要件定義書 3 章を直すときに書く） |
| 取り決め | 要件定義書 6.6（名前・UUID・JSON の分け方） | |

## 全体の形

```
M5StickS3（塩・こしょう・フライパン・つまみ）──BLE──┐
ESP32（電子レンジ）─────────────────────BLE──┤
                                                      ▼
カメラ（Python）──WebSocket（PC内）──▶  Go サーバー  ──WebSocket（PC内）──▶ Unity
```

サーバーの中は「入り口（BLE・WebSocket）」と「本体（鍋の状態・工程・採点）」に分け、入り口から本体へはチャンネルでイベントを渡す。
goroutine を使うのは入り口だけにして、本体は普通の関数で書く（Rust のときは tokio）。

## 段階

1 段階ずつ PR にして `main` に入れてから次を始める。

### ① デバイスの BLE 送信（`feature/ble-device`）

- 状態：**完了（2026-10-13）**
- 作るもの
  - `device/`：NimBLE-Arduino で周辺機器になり、6.6 のとおりに JSON を通知する。USB シリアルへの出力も残す
  - 画面に BLE の状態（接続中・待機中）を出す
  - `tools/ble_monitor.py`：Mac・Windows で BLE のデバイスを探してつなぎ、届いた JSON を表示する確認用ツール（Python・bleak）。サーバーを作る前に、デバイス側だけを確かめるのに使う
- 終わりの条件
  - `tools/ble_monitor.py` で、振る・回すと JSON が届く
  - 本体のリセット・Mac 側の切断のあと、自動でつながり直す
- テスト：Mac 上のテスト（`device/host_test/run.sh`）、実機で `ble_monitor.py`
- やったこと（2026-10-13）
  - デバイスの BLE 送信と `tools/ble_monitor.py` を作り、Mac で受け取れた。振り 10 回 × 2 で 10 件ずつ、取りこぼし 0 件（`docs/テスト記録.md`）
  - 本体のリセット後、3.7 秒でつながり直した

### ② Rust で BLE を受ける（`feature/server-ble`）

- 状態：**完了（2026-10-13）**
- 作るもの
  - `server/`：Cargo プロジェクト。btleplug で 6.6 のサービスを持つデバイスを探して全台につなぎ、通知を改行までつなげて JSON にして表示する。切れたらつなぎ直す
- 終わりの条件：Mac で `cargo run` して、振る・回すと JSON がターミナルに出る。切断・再接続も確かめる
- やったこと（2026-10-13）
  - `server/` を作り、Mac で受け取れた（`knob`・`battery`）。`cargo test` 5 件 OK
  - サーバーの再起動から再接続までが 11〜12 秒かかることがあったので、接続のタイムアウトを短くし、Ctrl+C では切断してから終わるようにした。6 回とも 2.4〜2.6 秒
  - Rust サーバーで振り 10 回 → 10 件。本体リセット後の再接続は Python の確認ツールで確認済み（3.7 秒）のため省略

### ③ サーバーの本体（`feature/server-core`）

- 状態：**完了（2026-10-13）**
- 作るもの
  - 6.2 のイベントの型（`enum`）、MAC アドレス → 役割の設定ファイル（6.5、TOML）
  - 本体：連番の重複を捨てる、振り → グラム、つまみ → 火の強さ。受信したものと出したものをファイルに記録する
  - Unity・カメラとの WebSocket は ③ のあとの段階で作る
- 終わりの条件：塩を振ると `season`、つまみを回すと `fire` のイベントがログに出る。本体の処理は Mac 上のテスト（`cargo test`）で確かめる
- やったこと（2026-10-13）
  - `event.rs`（イベントの型）、`config.rs`（設定ファイル）、`kitchen.rs`（本体）、`event_log.rs`（ログ）を作り、`main.rs` でつないだ。`cargo test` 21 件 OK
  - 実機：塩で 10 回振って `season` 10 件（合計 4.28g）、つまみで `fire` が 弱 → 中 → 強 → 中 → 弱 → 切。役割に合わない `knob` は無視された（`docs/テスト記録.md`）

### ④ 画面への配信とカメラの受信（`feature/server-ws`）

- 状態：**Mac で確認（2026-11-06）**。実機（デバイス・カメラ）とつないだ確認はまだ
- 作るもの
  - `server/src/ws.rs`：WebSocket（axum）。`/screen` の画面（Unity・three.js の試作）に 6.4 のイベントを全部配る。`/camera`（パス無しも）でカメラの 6.3 を受け取る
  - 本体：カメラの `position`・`swing`・`cut`・`add` を画面に流す。ピース数・フライパンに入った数を持つ。リセット（画面から `reset`）
  - `--no-ble`：デバイスの無い PC（Unity を作る PC など）で、カメラと画面だけ試す
- 終わりの条件：カメラから送った `cut` が画面に届き、画面の `reset` でサーバーの調味料が 0 に戻る
- やったこと（2026-11-06）
  - `cargo test` 29 件 OK（カメラの JSON・6.4 の形・リセット・WebSocket で画面 2 つに届く・カメラの行が届く）
  - `--no-ble` で起動し、カメラのふりをしたプログラムから送ったイベントが画面に届いた。three.js の試作（`screen/index.html`）がサーバーにつながり、`cut` でにんじんが切れた（`docs/テスト記録.md`）

### ⑤ サーバーを Go に移す（`feature/server-go`）

- 状態：**Mac で確認（2026-11-26）**。Windows の実機ではまだ
- 作るもの
  - `server/*.go`：Rust 版（`src/*.rs`）と同じ動きを Go で書く。BLE は `tinygo.org/x/bluetooth`、WebSocket は `coder/websocket`、設定は `BurntSushi/toml`
  - テスト：Rust 版の 29 件を `go test` に移し、Go で気をつける所（`5.0` の書き方・null・`tip` の数・ブラウザからの接続・画面の受け取り遅れ など）を足す
- 終わりの条件：同じ入力で、画面に届く JSON・表示・ログが Rust 版と同じ。Mac の実機（M5StickS3）で、振る・回す・切断・再接続・Ctrl+C のあとの再起動が Rust 版と同じように動く
- やったこと（2026-11-26）
  - `go test` 38 件 OK（`-race` でも OK）。Windows・Linux 向けにもビルドが通る
  - Rust 版と Go 版を並べて同じものを送り、画面に届く JSON 11 件・ログ 32 行が同じだった（違うのは読めない行のエラー文だけ）
  - 実機：起動して約 2.5 秒で `omamagoto-5C3C` につながった。Ctrl+C で切ってすぐ起動し直しても待たされない（`docs/テスト記録.md`）
  - macOS では、名前がスキャン応答にあるので、名前が届くまで最大 1 秒待ってからつなぐようにした
